# Обратимые эффекты в контракте модуля

Предложение команде GRACE. **v0.2, 2026-08-25** — переписано под GRACE 4.
Обкатано на реальном проекте: ClaudeBar (Rust + Win32, 23 модуля), мигрирован
на GRACE 4 в ходе подготовки этого текста.

> Для отправки в апстрим текст нужно перевести на английский: репозиторий
> `osovv/grace-marketplace` англоязычный.

---

## Коротко

Добавить в `MODULE_CONTRACT` два поля:

- **`EFFECTS`** — что модуль меняет **за своими границами**;
- **`REVERT`** — как это откатить.

И одно правило в линтере: `EFFECTS` не `none` при пустом `REVERT` — ошибка.

Поле не выдумано за столом: оно **стихийно возникает в свободном `NOTE`**, когда
автору нужно зафиксировать границу владения ресурсом. Предлагаем узаконить и
сделать проверяемым.

## Проблема: у GRACE есть пространственная ось, нет временной

GRACE 4 хорошо решает **пространственную** задачу композиции: `DEPENDS` в
контракте плюс зависимости тегами в `.grace/graph/*.xml` дают декларацию связей
и граф, по которому видно, кто на кого опирается.

Вторая ось — **временная**: что остаётся в системе, когда модуль удаляют. Про
неё в контракте нет ни слова. Следствие предсказуемо: обязательство «убрать за
собой» **негде объявить, поэтому его никто и не выполняет**.

Дело не в небрежности. Каждый эффект по отдельности пишется осознанно и
правильно. Теряется он на удалении — там, где про него уже никто не помнит.

## Доказательство: что осталось бы после удаления ClaudeBar

Прошли по всем 23 модулям и выписали, что каждый меняет снаружи себя
(полностью — в `effects-inventory.md`):

- каталог `%APPDATA%\claudebar\` целиком: две базы SQLite с WAL-файлами,
  растущий без ротации `voice.log`, история поиска, три подкаталога;
- `claudebar.ini` рядом с уже удалённым исполняемым файлом;
- **правки в чужих `settings.json` VS Code и Cursor** — подменён `window.title`;
  отката нет, а бэкап перезаписывается при каждой записи, то есть исходное
  значение теряется после второго вызова;
- **блоки хуков в `~/.claude/settings.json` и `~/.kimi-code/config.toml`** —
  после удаления они зовут несуществующие скрипты;
- возможно не остановленный Docker-контейнер.

Штатного удаления в проекте нет ни одного.

Последние два пункта — не мусор, а **поломка чужих программ**. Они и показывают,
что задача не косметическая.

## Три класса эффектов

У них разная цена ошибки, и откат устроен по-разному:

| Класс | Что это | Как откатывать |
|---|---|---|
| **своё** | создали целиком и владеем | удалить |
| **чужое** | правка в файле, которым владеет кто-то другой | вернуть **ровно нашу часть**, не тронув остальное |
| **процесс** | запущенное нами и живущее дольше нас | остановить |

Класс «чужое» — самый опасный. Здесь «удалить файл» это не откат, а новая
поломка.

## Предложение под GRACE 4

### 1. Поля в контракте исходника

```
// START_MODULE_CONTRACT
//   PURPOSE: ...
//   SCOPE: ...
//   DEPENDS: M-WINENUM
//   EFFECTS: своё:    создаёт %APPDATA%\claudebar\signals\; удаляет оттуда *.signal
//            чужое:   —
//            процесс: —
//   REVERT:  удалить каталог signals\ целиком
//   LINKS: M-SIGNAL
//   ROLE: RUNTIME
// END_MODULE_CONTRACT
```

Для «чужого» откат обязан быть точечным:

```
//   EFFECTS: чужое: ключ "window.title" в settings.json VS Code и Cursor
//                   (бэкап settings.json.claudebar-bak)
//   REVERT:  вернуть прежнее значение из бэкапа; если бэкапа нет — удалить
//            ТОЛЬКО наш ключ, файл целиком не перезаписывать
```

Модуль без внешних эффектов пишет `EFFECTS: none` — это тоже полезно: значит
его можно удалять свободно.

### 2. Точка внедрения в CLI — одна строка

В `src/project-utils.ts` уже есть проверка обязательных полей контракта:

```ts
for (const field of ["PURPOSE", "SCOPE", "DEPENDS", "LINKS"]) {
  if (!contract.fields[field]?.trim()) {
    issues.push(markupIssue("error", "markup.missing-contract-field", ...));
  }
}
```

Предлагаем добавить `"EFFECTS"` и `"REVERT"` в этот список плюс отдельное
правило:

```
markup.effects-without-revert — EFFECTS отличается от 'none', а REVERT пуст
```

Больше в линтере менять нечего: механика разбора полей контракта уже работает.

### 3. Граф (опционально, вторым шагом)

В `.grace/graph/*.xml` у модуля сейчас `Summary`, `Path` и зависимости тегами.
Добавить необязательный `<Effects>` рядом с `<Summary>` — тогда эффекты
становятся рёбрами «модуль → ресурс», и граф начинает отвечать на вопрос
**«кто ещё трогает этот каталог»**, то есть ловит конфликты владения.

Начинать с этого не нужно: поля в контракте дают пользу сразу, граф — оптимизация.

### 4. Верификация

Точка нового вида в `.grace/verification/*.xml`: «поставить → поработать →
откатить по `REVERT` → система в исходном состоянии». Обычный `Scenario`,
никакой новой схемы.

### 5. Что это даёт `grace-refactor` и `grace-execute`

Главная выгода. Агент, удаляющий модуль, **читает `REVERT` и выполняет его**,
вместо того чтобы догадываться.

Человек, работавший с проектом год, помнит про каталог в `%APPDATA%`. Агент —
нет. Он видит только то, что записано. Сейчас при удалении модуля агент
реконструирует эффекты из кода и промахивается тем вернее, чем аккуратнее
эффект спрятан за абстракцией.

## Три свидетельства из практики

Все три получены за один рабочий день на одном проекте.

**1. Инвентаризация окупилась до первой проверки.** Пока просто выписывали
эффекты по модулям, нашлись три долга, которых никто не искал: `voice.log` без
ротации; бэкап настроек редактора, затирающий сам себя со второго вызова;
отсутствие деинсталлятора у хуков агентов. Ни один не был багом в коде — все
трое были **незаписанным обязательством**.

**2. Конвенцию подхватили без просьбы.** Поля появились в семи контрактах.
Параллельная сессия, работавшая над новым модулем в том же репозитории, увидела
их в чужом коммите и **сама дописала `EFFECTS`/`REVERT` в свой контракт**,
правильно определив, что своё у неё только каталог иконок, а сигналы и письма —
чужие, читаются и не трогаются. Поле читается как естественная часть контракта,
а не как навязанная бюрократия.

**3. Непроверяемое тихо гниёт.** В этом проекте `grace lint` не работал: проект
был на GRACE 3, CLI четвёртой версии отказывался его валидировать. За это время
накопилось **20 ошибок разметки**, вскрывшихся при миграции разом. Самая
поучительная — в `voice.rs`: хвост после имени блока ломал разбор маркера, а
когда его убрали, вскрылась настоящая причина — внутри блока лежали контракты
функций. **Одна ошибка маскировала другую**, и обе жили, потому что их некому
было заметить.

Третье свидетельство — главный аргумент за то, что поля должны быть
**проверяемыми линтером, а не соглашением**. Соглашение без проверки протухает.

## Чем это отличается от Cordis

Идея не наша. Она формализована в статье
[_A Programming Paradigm for Spatiotemporal Composability_](https://github.com/cordiverse/paper)
(август 2026), на которой построен DeepSeek Harness. Там **рантайм** сам ведёт
обратную операцию для каждого изменения контекста — забыть физически невозможно.

GRACE не рантайм, а методология сборки кода, и такой гарантии дать не может.
Планка ниже и честнее: обязательство должно быть **записано и проверяемо**.
Забыть по-прежнему можно — но уже не молча.

## Ограничения, которые стоит признать сразу

- Проверка «в коде нет необъявленных эффектов» полнотой не обладает: эффект
  можно спрятать за абстракцией или внешней библиотекой. Ловим типовые случаи.
- `REVERT` прозой не исполняется автоматически. Следующий шаг — машинная форма
  (список путей и команд), но начинать стоит с прозы: она сразу даёт пользу
  ревьюеру и агенту.
- Поля стоят человеко-времени на каждом модуле. Оправдано там, где эффекты есть;
  для чистой логики это одна строка `none`.
- Добавление полей в список обязательных сломает линт у всех существующих
  GRACE-проектов разом. Разумный путь: сначала предупреждением, ошибкой — со
  следующей мажорной версии.
